# dsh-code-review 스킬 유지 관리

[English](maintaining-dsh-code-review.md) | [中文](maintaining-dsh-code-review.zh.md) | 한국어

[`dsh-code-review`](../../.agents/skills/dsh-code-review/SKILL.md) 스킬은 단 한 명의 지정 운영자가 비공개 주기 유지 관리 도구를 돌려 최신 상태로 유지합니다. 이 쿡북은 그 운영자와 역할을 이어받는 사람, 그리고 스킬 업데이트가 일회성 감사가 아니라 작은 주기 PR로 도착하는 이유를 알고 싶은 저장소 기여자를 위한 진입점입니다. 워크플로 자체는 [인간 리뷰 스킬 유지 관리 Agent Note](../../.agents/notes/proposed/process/2026-07-13-human-review-skill-maintenance.md)에 명세되어 있습니다.

## 유지 관리자가 받는 것

운영자는 래퍼를 수동으로 매일 실행하며, UTC 기준 이틀 창을 겹치게 사용합니다. 수동 주간 복구 실행은 7일 창을 사용합니다. 워크플로는 다음과 같습니다:

1. 선택한 창(일일 주기의 기본값은 UTC 기준 이틀, 주간은 7일)에서 병합 커밋이 `origin/master`에 도달 가능한 PR을 고릅니다. 병합 커밋에 도달할 수 없는 PR(부모가 스쿼시된 스택 브랜치)이나 250커밋 획득 상한을 넘는 PR은 실행을 중단하는 대신 `skipped-pulls.json`에 기록하고 건너뜁니다.
2. 병합 전 인간 리뷰 피드백을 커밋 앵커와 함께 수집한 뒤(인라인 댓글과 리뷰 제출), 피드백 시점 패치와 최종 착지 PR 패치를 비교합니다. 현재 GitHub 상태로는 강제 푸시에 안전한 피드백 시점 기준선을 제공할 수 없으므로 PR 대화 댓글은 수집하지 않으며, 대상 브랜치 전용 변경은 채택 증거에서 제외합니다.
3. 독립적으로 구성된 두 리뷰어 어댑터가 각 항목을 누가 작성했는지, 그 변경이 이를 채택했는지 분류한 뒤, 합의된 채택 항목을 현재 스킬과 대조해 분류합니다.
4. 주 어댑터가 완전한 개정 `SKILL.md` 초안을 작성하고, 두 어댑터가 같은 diff를 검토하며, 차단 발견이 있으면 둘 다 승인할 때까지 반복합니다.
5. 도구가 성공을 선언하기 전에 후보에 대해 `pnpm run doc-sync`와 `pnpm run lint`를 실행합니다.

각 실행은 운영자 머신에 아티팩트를 저장합니다. 저장된 diff, 후보 `SKILL.md`, 승격 매니페스트는 타임스탬프 이름으로 `~/dsh-code-review-outputs/` 아래에 놓입니다. 매니페스트는 소스 master 커밋과 스킬 blob, 소스 피드백 ID와 URL, 착지 증거 범위, 어댑터 판정, 게이트 결과를 기록하며, 어댑터별 원시 I/O는 비공개 임시 디렉터리에 남고 그 경로는 알림과 `~/Library/Logs/dsh-code-review-maintainer/` 아래 일일 로그에 기록됩니다. 유지 관리 워크트리 자체는 매 실행 후 깨끗하게 복원되므로, 운영자가 유지 관리 사본을 제자리에서 편집하려는 유혹을 받지 않습니다.

## 운영자가 후보 diff로 하는 일

실행이 후보를 만들면 `dsh-code-review-promote <timestamp>` 힌트와 함께 macOS 알림이 도착합니다.

1. **diff 자체의 타당성을 꼼꼼히 검토하세요.** 단순히 "다른 리뷰어들이 승인했다"는 이유로 무조건 수용하지 마세요. 운영자가 최종 결정을 내리는 것이 유지관리자 계약의 핵심입니다. 체크리스트의 불필요한 비대화, 과거 히스토리에 얽매인 서술, 단일 사례로부터의 섣부른 일반화(외삽), 기존 스킬 및 공식 문서와의 중복 여부를 주의 깊게 확인하세요.

   ```sh
   ls ~/dsh-code-review-outputs/                         # every candidate ever produced
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.diff
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.SKILL.md
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.manifest.json
   ```

2. **실행 아티팩트와 교차 확인하세요.** 승격 매니페스트는 제안된 규칙마다 소스 피드백과 착지 증거를 매핑하며, 어댑터별 상세 I/O, 합의, 채택 증거는 실행의 비공개 임시 디렉터리(로그에 표시된 경로)에 있습니다. 후보를 최소 하나 표본 검사하세요. 연결된 사용자/리뷰어 코멘트가 새로 추가되는 규칙을 충분히 뒷받침하고 있나요? 연결된 PR이 실제로 이를 채택했나요?

3. **다음 세 가지 중 하나를 정하세요:**
   - **폐기.** 저장된 후보를 삭제합니다. 도구는 다음 실행에서 현재 스킬이 그때 말하는 내용에 따라 같은 피드백을 다시 검토합니다.

     ```sh
     rm ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.{diff,SKILL.md,manifest.json}
     ```
   - **배치.** 업데이트가 작고 향후 업데이트와 합칠 수 있다면 후보를 따로 보관합니다. 소스 스킬 검사는 여전히 적용되며, `master`가 먼저 바뀌면 분석을 다시 실행하거나 수동으로 리베이스한 뒤 diff를 다시 검토합니다.
   - **승격.** 저장소의 깨끗한 `master` 체크아웃에서 승격 헬퍼를 실행합니다. 헬퍼는 `master`를 새로 고치고 현재 스킬이 기록된 소스 blob과 일치하는지 검증하고, 저장된 diff를 적용한 뒤 소스 피드백 URL 또는 ID, 착지 커밋 범위, 원래 실행, 검사, 운영자 편집을 본문에 나열한 초안 PR을 엽니다. 더 새로운 지침을 덮어쓰지 않고 스킬 드리프트에서 멈춥니다. 운영자는 여전히 GitHub에서 PR을 검토해 병합하거나 닫습니다.

     ```sh
     cd ~/path/to/deepseek-harness   # clean master
     dsh-code-review-promote 2026-07-16T02-00-00Z
     ```

4. **어댑터 출력을 그대로 커밋하지 마세요.** 승격 중의 작은 편집(문구 다듬기, 소스 PR의 맥락에서만 말이 되는 예제 제거, 규칙을 기존 규칙에 접기)은 예상된 일이며 워크플로가 의존하는 "리뷰어 판단"을 보존합니다. 병합 전에 브랜치를 amend하세요.

## 실행이 후보를 만들지 않을 때

비어 있지 않은 모든 분류 단계가 유효한 어댑터 결과를 하나 이상 만든 뒤에는 이것이 일반적인 경우입니다. 도구는 일일 로그에 "후보 없음"을 기록하고, 알림 피로를 피하려고 알림을 보내지 않으며 넘어갑니다. 스킬 업데이트가 없는 날은 워크플로가 올바르게 동작한 것이며 정체가 아닙니다.

## 중단과 인계

메커니즘은 한 머신에 있습니다. 운영자가 발생할 때 처리하는 중단은 다음과 같습니다:

- **일일 실행 누락.** 이틀 겹침 창이 하루 건너뛴 것을 자동으로 잡습니다. 더 긴 공백은 `DSH_CODE_REVIEW_SINCE=<Nd>`로 래퍼를 수동 실행해 복구합니다. 겹치는 창은 멱등입니다. 현재 스킬에 이미 있는 지침은 `covered`로 분류되어 후보로 다시 들어오지 않습니다.
- **어댑터 제공자 장애.** 두 리뷰어 명령이 바이트 단위로 동일한 실행 파일로 해석되면 도구는 실행을 거부합니다. 어댑터 응답이 스키마나 id 검증에 실패한 단일 배치는 배치 수준에서 실패 폐쇄되고(그 배치의 모든 항목을 불명확으로 표시) 실행은 계속되며, 원시 출력은 디버깅용으로 보존됩니다. 어떤 작업에서든 비어 있지 않은 배치에 대해 두 어댑터 중 하나라도 유효한 결과를 내지 못하면 실행이 실패하고 실패 기록을 쓰고 운영자에게 알립니다. 전체 제공자 장애를 "후보 없음"으로 축소하지 않습니다.
- **다른 유지 관리자에게 인계.** 현재 것을 대체하는 후속 Agent Note를 엽니다. 즉 메커니즘을 저장소로 옮기거나 새 운영자의 비공개 설정을 기록합니다. 도구를 조용히 이전하지 마세요. Agent Note의 Risks 섹션에 있는 "단일 유지 관리자 버스 팩터"가 인계에 문서화된 결정이 필요한 이유입니다.

## 운영자의 비공개 설정이 사는 곳

도구 소스, 리뷰어 어댑터, 제공자 자격 증명, 스케줄러는 운영자의 비공개 인프라이며 설계상 이 저장소 밖에 있습니다(Agent Note의 "Where the mechanism lives" 섹션 참고). 이 쿡북과 Agent Note는 **워크플로가 보장하는 것**을 설명하고, 그 보장이 **어떻게** 구현되는지는 비공개 인프라의 관심사입니다. 새 운영자라면 Agent Note의 `## Proposal` 섹션이 여러분이 구현할 명세입니다.
