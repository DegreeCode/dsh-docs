# 스택 PR 체인 전체에서 리뷰에 응답하기

[English](responding-to-pr-review-on-a-stack.md) | [中文](responding-to-pr-review-on-a-stack.zh.md) | 한국어

리뷰 댓글은 의존 스택(`A ← B ← C …`)의 여러 PR을 대상으로 할 수 있습니다. 그 체인은 GitHub의 공식 스택 기능으로 연결된 상태로 유지하세요. 이 가이드는 리뷰 수정의 배치와 전파를 소유하고, [dsh-merging-stacked-prs](../../.agents/skills/dsh-merging-stacked-prs/SKILL.md) 스킬은 연결 검사와 착지를 소유합니다.

## 기본 규칙

1. **PR 브랜치마다 워크트리 하나.** 각 PR의 수정은 그 PR의 자체 워크트리에서 이루어지며, 병렬 수정은 체크아웃을 공유하지 않습니다.
2. **GitHub의 Stack 객체가 기준(Authoritative Source)입니다.** 베이스 브랜치가 기대 의존 순서를 세우고, `PullRequest.stack`과 `stackEntry.position`이 GitHub이 그 순서를 인식함을 증명합니다. 그 필드를 확인하지 않고 일치하는 브랜치 체인을 공식 스택으로 취급하지 마세요.
3. **수정은 그 문제를 도입한 PR에 착지한 뒤 스택 위로 흐릅니다.** PR `B`의 댓글이 `B`가 도입한 코드를 지적하면, `B`에서 고치고 `B`를 `C`로 전파하세요. `C`도 그 파일을 담고 있더라도 마찬가지입니다. 수정을 하위에서 시작하면 `B`는 고치지 않은 코드를 배포하는 상태로 남고 `B`의 리뷰어에게 수정이 보이지 않습니다.
4. **각 리뷰 수정은 별도 커밋으로 남습니다.** 나중 리베이스가 OID를 바꿀 수 있지만, 리뷰된 수정을 브랜치 이력에서 amend로 지우지 마세요. 아직 푸시하지 않고 리뷰되지 않은 자신의 작업만 amend합니다.
5. **머지 포워드와 리베이스를 의도적으로 고릅니다.** 리뷰 후 두 이력 모두 허용됩니다. 히스토리를 재작성한 푸시는 `--force-with-lease`로 안전하게 보호되어야 하며, 그사이에 전진한 원격 브랜치를 덮어쓰지 않고 중단해야 합니다. 무조건 덮어쓰는 단순 `--force`는 금지됩니다.

## 스택을 통해 댓글 해결

1. 행동하기 전에 모든 댓글을 본질 기준으로 분류하세요. 코드로 그 주장을 검증하세요. 올바른 증상을 지적한 리뷰어도 원인은 잘못 진단할 수 있습니다.
2. 수락한 발견마다 원래 PR을 매핑해 그곳에서 고칩니다.
3. 수정된 계층을 영향을 받는 모든 자식에 순서대로 전파합니다:
   - **머지 포워드:** 수정된 부모 브랜치를 자식에 병합하고, 자식을 검증한 뒤 위로 계속 진행합니다. 진행 중인 체크포인트를 모두 보존하세요.
   - **네이티브 캐스케이딩 리베이스:** `gh stack rebase`로 다시 쓴 계층을 검증한 뒤 `gh stack push`로 게시하거나, 먼저 게시할 수 있는 `gh stack sync`를 사용한 뒤 [dsh-pre-push-checks](../../.agents/skills/dsh-pre-push-checks/SKILL.md)에 따라 동기화 직후 검증을 수행합니다.
4. 위임한 수정은 신뢰하되 검증하세요. 하위 에이전트의 보고는 의도를 설명할 뿐 실제로 무엇이 반영됐는지는 아닐 수 있습니다. 실제 트리에서 게이트를 직접 다시 실행하고, 회귀 가드라면 고치지 않은 코드에서 실패함을 증명하세요(회귀를 도입해 빨간불을 확인한 뒤 되돌립니다). 버그가 있어도 통과하는 테스트 가드는 아무것도 보호하지 못합니다. 하위 에이전트가 문제를 이미 처리된 것으로 재구성하면 직접 파고들라는 신호입니다.
5. 리뷰 스레드에 답장하세요(`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`). 최상위 댓글이 아니라 스레드에 답하고, 수정 내용과 그것을 담은 현재 커밋 또는 헤드를 밝힙니다.
6. 이력을 다시 쓴 푸시 후에는 미해결 스레드, 승인, 병합 가능성, 검사를 다시 읽으세요. 강제 푸시된 커밋 OID나 오래된 인라인 앵커는 그 발견이 여전히 해결되었음을 보여 주는 현재 증거가 아닙니다.
7. 공식 스택 절차로만 착지하세요. PR이 아직 연결되지 않았다면 착지 스킬이 같은 작성자 체인을 자동 연결하고, 작성자가 섞인 경우 연결 전에 물으며, 네이티브 스택 지원이 없으면 강제로 멈춥니다.

## 검증

- 수정된 모든 PR의 현재 diff에, 문제를 도입한 계층의 의도한 수정이 들어 있습니다.
- GraphQL이 기대 순서대로 하나의 공식 스택을 보고하며, 각 자식의 부모 대비 diff에는 그 자식의 변경만 보입니다.
- 미해결 스레드, 승인, 병합 가능성, 검사는 이력을 다시 쓴 모든 푸시 후에 재감사되었습니다.
- 스택 상단뿐 아니라 영향을 받는 모든 PR에서 해당 게이트가 통과합니다.
