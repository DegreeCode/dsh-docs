## 1. 버전과 릴리스 기반 고르기

유효한 판별자가 안전하지 않은 해석을 막을 수 없을 때만 형식을 올립니다. 헤더, 이벤트 봉투, 이벤트 시맨틱, 재구성에 대한 구조 변경은 자동 인상이 아니라 [판독기 호환성 규칙](../../.agents/notes/implemented/process/2026-10-08-session-reader-compatibility-review.md) 아래에서 평가해야 합니다. 안전한 동일 버전 진화는 [타입 변경 절차](reviewing-persistence-type-changes.ko.md)로 기록합니다. 세션 형식 정수를 패키지 릴리스 버전, SQLite 스키마 버전, 프로젝션 단위 버전, 프로토콜 래퍼 버전과 구분하세요.

인상이 필요할 때 [버전/상태](../session-format-status.ko.md)에서 수락되었거나 게시된 버전을 N이라 합니다. V4가 수락된 뒤라면 그 인상은 V4 게시가 기록되기 전에도 V5를 요구합니다. 검토된 동일 버전 진화에는 그 단계가 필요하지 않습니다.

N+1에는 공유 `release/*` 통합 기반을 사용하세요. 기반 변경이 기록기, 코덱, 카탈로그 배선, 아이덴티티 마이그레이션, 검증을 추가합니다. 각 독립 자식 브랜치는 그 기반에서 만들고 PR은 다른 독립 자식의 브랜치가 아니라 릴리스 브랜치를 대상으로 하세요. 각 자식은 구조 변환, 검증기, 소비자, 테스트를 같은 인접 마이그레이션 패키지에 추가합니다. 검토 순서를 나타내려고 추가 버전을 할당하지 마세요. 검토된 자식을 PR로 릴리스 브랜치에 병합한 뒤 릴리스 전에 결합 결과를 검증합니다. 릴리스 브랜치의 강제 푸시와 삭제 보호를 준수하고, 강제 동기화하지 마세요.

배포된 코덱은 수락된 해석을 보존합니다. 현재 버전 코덱은 명시적으로 판별된 변형을 허용하면서도 역사적 가독성을 유지할 수 있습니다. 더 오래된 코덱을 넓혀 현재 기능을 허용하지 마세요. N→N+1 변환기는 N+1이 출시된 뒤에도 출력이 N+1과 호환되는 한 수정이나 추가 역사 사례 지원을 받을 수 있습니다. 수정은 이후 변환에 영향을 주며 기존 N+1 후속에는 영향을 주지 않습니다. 바뀐 매핑과 기존 출력 지원 지속을 문서화하고, 새 대상 표현에는 판독기 호환성 규칙을 적용하세요.

동일 버전 로그는 인접 마이그레이션을 우회하고 재개 후 역사적 레코드 변형과 새 레코드 변형을 섞을 수 있습니다. 따라서 각 정수는 하나의 고정 스키마가 아니라 지원되는 표현 패밀리를 식별합니다. 소유 판독기는 그 변형을 보존하고 구분해야 하며, 다음 아웃바운드 마이그레이션이 이를 처리해야 합니다. 동일 버전 마이그레이션을 추가하거나 정규화를 `restoreCurrent`에만 의존하지 마세요. 변환된 검증을 쓰는 현재 버전 JSONL 읽기는 그 훅을 우회합니다. 중간 통합 형식에는 일회용 격리 하네스 홈을 사용하고, 커밋된 세대를 다시 쓰거나 실제 사용자의 홈을 쓰지 말고 변경되지 않은 역사적 입력에서 바뀐 인접 변환을 다시 실행하세요.

기록기를 바꾸기 전에 [아카이브 명령](../persistence-changes/historical-formats/README.md#maintain-coverage)으로 완전한 영속화 스키마를 보존한 뒤 `docs/persistence-changes/historical-formats/vN.*` 아래에 이중 언어 형식 참조를 추가하세요. 이전 레코드는 모두 보존합니다. 형식 커버리지 검사는 새 기록기 아래의 모든 정수에 자체 문서가 있기를 요구하며, 현재 생성 카탈로그는 새 기록기만 포괄합니다.

## 2. 아이덴티티 에지 추가

N→N+1 라이브러리는 마운트되는 플러그인이 아니라 패키지 체크리스트를 따라 만드세요. 아이덴티티 본문 변환은 최초 배선 골격일 뿐입니다. [V2→V3 명세](../../packages/session/session-format-v2-to-v3/README.md#v2-to-v3-specification)는 명시적 변환과 보존 규칙의 고정 예시이며, 확장하거나 아이덴티티 변환으로 취급할 에지가 아닙니다.

숫자 `from: N`과 `to: N+1`, 익스포트 경로, 그리고 내보낸 마이그레이션·소스 코덱·대상 코덱·대상 헤더 검증기·대상 복원기를 담아 `dsh.sessionFormatMigration`을 선언하세요. 앞선 에지 패키지가 내보낸 소스 코덱을 재사용하고 그 패키지에 의존하세요. 배포된 코덱을 복사하거나 재정의하지 마세요. 새 패키지에서 대상 코덱과 검증기를 내보냅니다. 에지를 카탈로그의 직접 의존성으로 추가하고 워크스페이스의 TypeScript 경로와 프로젝트 참조를 추가하세요.

새 에지 선언과 함께 [코어 세션 타입](../../packages/core/session/src/types.ts)의 `SESSION_FORMAT_VERSION`을 N+1로 설정한 뒤 카탈로그를 생성하세요. 아래 명령은 선언된 체인만 생성하며 새 버전을 구현하지는 않습니다:

```sh
pnpm run gen-session-format-catalog
```

[생성기](../../scripts/gen-session-format-catalog.ts)는 0부터 기록기 버전까지 모든 단계에 인접 패키지가 정확히 하나씩 있고, 디렉터리/패키지 이름이 일치하며, 인접 코덱 익스포트가 일치하고, 의존성이 선언되어 있기를 요구합니다. 구멍, 중복되거나 여분인 에지, 알 수 없는 메타데이터 멤버, Session을 피어 및 개발 의존성으로 공유하지 않는 카탈로그를 거부합니다. `generated.ts`를 손으로 고치지 말고 선언을 고치세요. 카탈로그는 빌드 시 정적이며, 플러그인 마운트가 역사적 가독성을 좌우해서는 안 됩니다.

## 3. 아티팩트별 단계와 검증 구현

아티팩트 전체를 배열에서 배열로 바꾸는 마이그레이터가 아니라 [Stage 인터페이스](../../packages/session/session-format/src/types.ts)를 사용하세요. 불변 `SessionFormatMigration` 선언이 `migrateHeader`, `validateTargetHeader`, `createStage`를 제공합니다. `createStage`를 호출할 때마다 소스 아티팩트 하나에 대한 독립 상태가 만들어집니다. 카운터, 대기 중 이벤트, 참조 맵을 그곳에 두고, 가변 stage를 세션 간에 공유하지 마세요.

`transformEvent(event, context)`, `transformRun(run, context)`, `finish(context)`를 구현하세요. `context.emitEvent`나 `context.emitRun`으로 동기적으로 내보내며, 한 호출이 0개, 1개, 여러 개의 출력을 만들 수 있습니다. stage가 코덱 소유의 컴팩트 실행을 직접 소비하게 하거나, 중간 배열을 구체화하지 않고 `run.expand()`를 순회하게 하세요. 스케줄링은 호출자가 소유하며, 체인은 다운스트림 단계 전에 업스트림 단계를 끝냅니다.

상속된 컷은 물리적 행 개수가 아니라 논리적 이벤트 개수로 취급하세요. `headerInheritedEventCount`는 EOF 전에 알려진 경우에만 노출하고, `finish`가 정확한 대상 컷을 반환합니다. 카디널리티를 바꾸는 앞선 에지 때문에 생성 시점에 그 개수를 알 수 없을 수 있습니다. 필요하면 검증된 시드 마커에서 이를 도출하고, 직접 N 입력뿐 아니라 지원되는 각 역사적 세대에서 N+1까지 시드된 다중 홉 복원을 테스트하세요. 알 수 없는 컷에 0을 대입하지 마세요.

새 에지의 이벤트 수용과 변환 규칙을 명시적으로 정의하세요. [V2→V3 소스 감사](../../packages/session/session-format-v2-to-v3/README.md#source-audit)와 [알파 V0→V1 규칙](../../.agents/notes/implemented/architecture/2026-08-31-alpha-historical-unknown-event-refusal.md)은 그 배포된 에지들의 정책을 소유할 뿐 새 에지의 정책은 아닙니다. 어느 쪽도 모든 에지로 일반화하지 마세요. 구조나 이벤트 위치를 바꾸려면 소스 이벤트, 페이로드 멤버, 참조를 분류하고 불투명 데이터가 계속 유효할 수 있는지 명시적으로 결정해야 합니다. [동일 버전 보유](../../.agents/notes/implemented/architecture/2026-08-30-retain-ignorable-external-session-events.md)만으로는 구조 변환이 안전하다고 증명되지 않습니다. 대상 시맨틱을 검증하고 새로 수용한 사례마다 거부 반례를 주세요. 지원되지 않는 변환을 숨기려고 더 오래된 에지를 넓히지 마세요.

`appendPluginRecord()`가 쓰는 플러그인 레코드는 `plugin:` 네임스페이스의 무시 가능 이벤트이며, 실험 패키지가 타입으로 다시 읽습니다. 대상 형식이 이를 표현할 수 있으면 그 이름으로 앞으로 나르고, 그렇지 않으면 어떤 레코드를 버리는지 에지 README에 밝히세요. [무시 가능 이벤트 결정](../../.agents/notes/implemented/architecture/2026-08-30-retain-ignorable-external-session-events.md)이 이를 최선 노력 기준으로 유지합니다. 저장된 레코드에 [실험 영속화 카탈로그](../experimental-persistence-catalog.ko.md) 선언이 없어도 이 정책을 적용하세요.

네이티브 기록기 출력을 변환 오라클로 사용하세요. 같은 녹화 LLM 메시지, 도구 출력, 기타 입력을 옛 기록기와 대상 기록기로 다시 재생합니다. 형식 정규화 헬퍼를 쓰기 전에 마이그레이션된 옛 출력과 원시 대상 출력을 비교하고, 문서화된 휘발성 필드만 마스킹하세요. V4에서는 일반 도구 결과가 일반 콘텐츠 블록을 가진 평평한 도구 역할 메시지가 됩니다. 이론상 허용되는 옛 구조만으로 새 코어 콘텐츠 타입을 정당화할 수는 없습니다.

알파 변환기는 구현되고 증거가 있는 매핑이 없는 역사 사례는, 그 밖에는 유효한 로그라도 명시적으로 거부할 수 있습니다. 소스는 그대로 두고 부분 후속은 게시하지 마세요. 지원을 넓힐 때는 실제 코퍼스와 재현 가능한 기록기를 선호하고, 사용자 코퍼스는 읽기 전용으로 살피며 정제된 회귀 픽스처를 만드세요.

에지 README에는 대상 형식에 필요한 식별자와 필드 매핑만 이유와 함께 문서화하세요. 확장 가능하다는 이유만으로 직접 소스 종류나 일반 메타데이터에 네임스페이스를 추가하지 마세요. 불투명 중첩 데이터는 보존하세요. 알파 변환기는 새 대상 의미를 얻게 될 예상치 못한 소스 필드를 해석을 지어내는 대신 거부할 수 있습니다.

새 에지의 README를 그 단일하고 완전한 변환·수용 카탈로그로 유지하고 [V2→V3 명세](../../packages/session/session-format-v2-to-v3/README.md#v2-to-v3-specification)를 따르세요. 변환되는 모든 헤더, 이벤트, 메시지 슬롯, 페이로드 필드를 열거하고, 정확한 이름 변경·충돌 규칙, 보존되는 id·좌표·참조·상속 컷, 외부 전제, 거부·불투명 데이터 정책, 지원되지 않거나 미뤄진 동작을 밝히세요. 역사적 소스 변환과 네이티브 대상 수용을 분리하고, 어느 코덱·복원기·설치된 검증기·복구 정책이 각 검사를 수행하는지 밝히세요. 선언된 스키마보다 의도적으로 좁은 검증은 기록하세요. 이 카탈로그는 코드와 같은 변경에서 갱신하며, 생성된 스키마 인벤토리나 PR 설명이 이를 대체하지 않습니다.

`sessionFormatCatalog.createRestore(header, { recovery: 'strict', validation: 'current' })`로 엄격 복원을 증명하고, 행을 순서대로 주입하며 `finish()`를 호출하세요. 이는 물리적 디코딩, 전체 체인, 설치된 현재 세션 검증을 실행합니다. 프로덕션의 복구 가능/변환 정책은 엄격 픽스처 및 게시 검증을 대체하지 않습니다. 에지가 실제로 수행하는 것보다 더 엄격한 소스 검증을 주장하지 말고 문서화된 역사적 검증 예외를 보존하세요.

<a id="current-version-consumers"></a>
## 4. 현재 버전 소비자 갱신

세션 생성/복원, JSONL 파일 이름 선택과 게시, 카탈로그의 현재 인코더/복원기, 프로젝션 캐시 생성 아이덴티티, 재생·스냅샷 정규화, [물리적 픽스처 레이아웃 검증](../../scripts/session-fixture-layout.ts), TypeScript/Python SDK 기록을 포함해 각 현재 버전 소비자를 추적하세요. 값이 현재를 의미할 때는 기록기 상수를 사용하고, 배포된 코덱과 역사적 픽스처에는 리터럴 역사 버전을 유지하세요. 현재 문서와 생성 참조는 그 소유자를 통해 갱신합니다.

무관한 버전을 자동으로 올리지 마세요. 요청 래퍼의 `sessionFormatVersion`은 내장된 세션 세대를 식별하며, 그 바깥 스키마 버전은 자체 의미를 가집니다. 마찬가지로 프로젝션 단위 상태 버전은 캐시의 세션 세대 아이덴티티를 대체하지 않습니다.

읽기와 쓰기 경로를 모두 검증하세요. 헤더 전용 목록은 본문을 읽거나 게시해서는 안 됩니다. 역사적 읽기 열기는 쓰지 않고 마이그레이션된 메모리 내 아티팩트를 반환할 수 있으며, 쓰기 열기는 append 전에 최종 현재 후속만 검증하고 게시해야 합니다. 소스 경로, 바이트, inode는 그대로입니다. 더 새롭거나 잘못된 선택 세대가 선행 세대로의 폴백을 일으켜서는 안 됩니다. [준비 결정](../../.agents/notes/implemented/architecture/2026-09-05-read-only-session-migration-preparation.md)이 게시 시점을 소유합니다.

<a id="snapshot-successors"></a>
## 5. 스냅샷 후속 생성

[스냅샷 소유권](../../snapshots/AGENTS.md)과 [스냅샷 라이브러리](../../packages/test-support/session-snapshot/README.md)를 읽으세요. [코퍼스 정책](../../scripts/session-snapshot-corpus-policy.ts)은 선언된 기준선을 재생 입력으로 유지해 업그레이드가 인접 체인을 훈련하도록 하며, 기록기 인상이 그 코퍼스 갱신을 요구하지는 않습니다. 현재 세대 후속이 필요하면 소유 시나리오를 고르고, 각 역사적 파일을 유지하며, 대상 버전의 정규 부모·자식 파일 이름을 사용하세요. 선행을 대상 파일 이름으로 이름 변경하거나 헤더만 바꾸지 마세요.

변경되지 않은 재생 입력이라면 소유자에서 키 없는 새로 고침을 사용한 뒤 쓰기 없이 재생하세요. 이 SDK 명령은 `text-turn`과 체크아웃의 기록기 버전을 사용합니다. 그 버전을 생성하는 데 사용하기 전에 N+1을 구현하고 배선하며, 기능에는 실제 영향을 받는 소유자를 고르세요:

```sh
pnpm run test:snapshot:refresh snapshots/sdk/sdk.snapshot.ts -t text-turn
pnpm run test:snapshot snapshots/sdk/sdk.snapshot.ts -t text-turn
```

새 세대, 요청 사이드카, 프로토콜 출력을 함께 검토하세요. 모든 선행이 바이트 단위로 동일하고 부모/자식 역할이 연속적인지 검증합니다. 선택은 숫자가 가장 높은 세대를 사용하므로, 공유 참조를 소유자의 선택된 부모로 갱신하세요. 압축 레이아웃 마이그레이터를 버전 업그레이더로 사용하지 마세요. 모델 전사를 바꿔야 하면 시나리오 소유자가 [테스트 정책](../testing.ko.md) 아래 라이브 녹화를 사용하며 필요한 제공자 키가 있어야 합니다.

보유 기준선보다 오래된 사례는 `snapshot.yml`의 `sessionFormat.version`과 지원되는 `coverage` 이름으로 명시적으로 유지하세요. 기록과 새로 고침은 고정된 세션 픽스처를 건드리지 않습니다. 집중된 직접 에지, 다중 홉, 압축 행, 재시도/실패, 배포 프로필 커버리지를 유지하면서 현재 세대에 맞게 [코퍼스 정책](../../scripts/session-snapshot-corpus-policy.ts)을 갱신하세요. 코퍼스와 두 SDK 투영을 확인하고, 검증 실패를 잠재우려고 무관한 시나리오를 대량 새로 고침하지 마세요.

<a id="validate"></a>
## 6. 통합 결과 검증

저장소 루트에서 실행하세요. 이 명령들은 카탈로그 선언, Stage 구성, 배포된 V2→V3 에지, 세대 선택을 검사합니다. 기준선일 뿐이므로 새 에지에는 집중 커버리지를 추가하세요:

```sh
pnpm run verify-session-format-catalog
pnpm exec vitest run scripts/gen-session-format-catalog.spec.ts packages/session/session-format/tests packages/session/session-format-v2-to-v3/tests packages/session/session-format-catalog/tests
pnpm run test:snapshot scripts/session-snapshot-corpus.corpus.ts
```

새 에지를 구현한 뒤에는 실제 테스트 경로를 집중 Vitest 실행에 추가하세요. 실제 diff가 선택하는 변경된 JSONL, 재생, 프로젝션, SDK 테스트와, 그 경로가 바뀔 때 빌드된 게시 Worker 스모크를 추가합니다. 성공적인 엄격 마이그레이션, 골격의 아이덴티티 보존, 잘못된 이벤트 및 알 수 없는 필수 이벤트 거부, 결정적 반복 복원, 독립적 동시 stage 상태, 시드된 다중 홉 컷, 변경되지 않은 선행, 폴백 없음을 요구하세요. 추론한 전체 스위트 결과가 아니라 정확한 명령과 실패를 보고하세요.

중복 결정 기록을 추가하는 대신 [소유 Agent Note](../../.agents/notes/implemented/architecture/2026-08-31-released-session-format-migrations.md)를 갱신하세요. [릴리스 기록](../session-format-status.ko.md#기록-갱신)은 게시 전까지 그대로 두고, 게시 후 검증된 릴리스 증거로 갱신합니다. 관련 활성 노트가 대체되는지 감사하고, 독립 근거는 유지하며 아카이브된 노트는 동결한 채 두세요. 다국어(이중 언어) 설명 텍스트는 원문과 번역본을 함께 갱신하고, 저장소 도구로 변경된 문서 쌍마다 페어링 기록을 다시 생성한 뒤 문서 검사를 실행하세요:

```sh
pnpm run verify-translation-pairing --write docs/cookbook/adding-a-session-format-version.md
pnpm run test:docs
pnpm run doc-sync
pnpm run lint
git diff --check
```

<a id="v4-corpus-trial"></a>
### 개발자 V4 코퍼스 시험

기록기가 V4인 설치된 기여자 체크아웃에서 일회성 [마이그레이션 스크립트](../../scripts/migrate-sessions-to-v4.ts)를 사용하세요. 시작 전에 대상 루트를 쓰는 DSH 프로세스를 중지해 기록기 잠금과 변하는 자식 로그가 마이그레이션을 막지 않게 하세요. 저장소 루트에서 실행합니다:

```sh
pnpm run migrate:sessions-to-v4
```

기본 루트는 `~/.dsh/sessions`입니다. 다른 코퍼스에는 `--sessions-dir /path/to/sessions-copy`를, 사용법에는 `--help`를 사용하세요. 동시 작업은 기본적으로 사용 가능한 CPU 수를 16으로 제한한 값이며, `--jobs N`은 더 큰 전문가 재정의를 포함해 양의 안전 정수를 받고 `--jobs 1`은 순차 실행합니다. 제한된 큐는 코퍼스 크기와 무관하게 그만큼의 세션만 한 번에 엽니다. 각 역사적 세션은 정상적인 잠금·검증 게시 경로를 거쳐 변경되지 않은 소스 파일 옆에 V4 후속을 만듭니다. 기존 V4 세션은 읽기 전용으로 열리며, 다시 실행해도 재변환하지 않습니다. 스크립트는 모델 요청을 하지 않고 변환·거부 규칙을 바꾸지 않습니다.

터미널은 각 세션의 선택 파일, 버전, 진행, 결과, 경과 시간을 보고합니다. 개별 오류가 이후 세션을 멈추지 않습니다. 최종 요약은 모든 실패와 전체 진단 로그를 시스템 임시 디렉터리 아래에 나열하며, 실패가 하나라도 있으면 0이 아닌 종료 상태를 반환합니다. JSON도 출력하고 `migration.log` 옆에 같은 보고서를 `summary.json`으로 저장합니다. 즉 소스 버전·결과별 개수, 그룹화된 실패 이유, 입력별 진단, 런타임 세부, 두 보고서 경로입니다. 알려진 진단은 이벤트 타입, 예상치 못한 멤버, 자식 로그 관련성, 시퀀스 번호를 노출하고, 인식되지 않는 오류는 원인을 추론하지 않고 메시지를 유지합니다. 마이그레이션 문제를 보고할 때 이 보고서들을 포함하세요. 이 실행 중 변환된 세션은 이미 V4인 세션과 구분됩니다.

동시 변환은 자식이 V4를 게시할 때 부모의 자식 증거를 무효화할 수 있습니다. 오직 그 소스 변경 오류만 모든 초기 작업이 끝난 뒤 순차 재시도 한 번을 받으며, 손상, 지원되지 않는 형식, 잡힌 잠금은 즉시 보고됩니다. 완료 줄은 원래 입력 인덱스와 별도의 완료 개수를 유지하므로 순서가 뒤바뀐 결과도 읽을 수 있습니다.

<a id="final-v3-vocabulary"></a>
### V4 게시 전 최종 V3 이벤트 어휘

게시된 형식은 V3이고 통합 기록기는 V4인 동안에도 master는 유효한 V3 이벤트 타입을 추가할 수 있습니다. master 통합이 있을 때마다, 첫 V4 게시 전에 마이그레이션이 소유한 `RELEASED_V3_EVENT_TYPES`를 그 새로 고침이 사용한 최신 V3 기록기 커밋과 비교하세요. 로컬에서 검증된 `origin/master`가 아직 V3를 쓰는 동안 불변 전체 id를 캡처하세요:

```sh
V3_SOURCE_REF="$(git rev-parse --verify 'origin/master^{commit}')"
pnpm run verify-v3-event-vocabulary --source-ref "$V3_SOURCE_REF"
```

검증기는 그 로컬 커밋만 읽고 정확한 이벤트 이름 동등성을 요구합니다. 누락된 V3 이름, 여분으로 복사된 이름, V3가 아닌 소스 기록기를 거부합니다. 특히 V4 전용 `developer/message`는 동결된 V3 집합에 들어가면 안 됩니다. 각 차이를 V3 페이로드, 필요한 변환, 대상 수용, 소비자와 비교해 검토하세요. 이름만 추가하는 것으로는 완전한 마이그레이션이 성립하지 않습니다. 새 소스 이벤트를 수용하기 전에 대응하는 마이그레이션 회귀를 추가하세요.

이 명령은 원격 최신성을 가져오거나 확립하지 않습니다. 릴리스 운영자는 선택한 커밋이 통합에 포함된 최신 V3 기록기임을 검증해야 하며, 오래된 원격 추적 ref나 더 오래된 핀에 대한 통과 결과로는 부족합니다. 검사한 id를 릴리스 검증과 함께 기록하세요. master가 이미 V4를 쓴다면 현재 master를 해석하지 말고 기록된 최종 V3 커밋을 재사용하세요. V4가 출시된 뒤에는 V3 어휘를 그 역사적 소스에 묶어 두며, 이후의 V4 이벤트 추가가 이를 갱신하지 않습니다. 정규 정적 CI는 가변 master ref에 의존하지 않습니다.
