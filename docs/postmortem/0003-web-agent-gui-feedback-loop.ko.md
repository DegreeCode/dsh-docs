# 포스트모템 0003: 웹 에이전트가 현재 GUI 대신 대체 서버를 검증했습니다

[English](0003-web-agent-gui-feedback-loop.md) | [中文](0003-web-agent-gui-feedback-loop.zh.md) | 한국어

상태: 해결됨

## 요약

웹 에이전트가 GUI 소스를 수정했지만 세션을 호스팅하는 URL과 프로세스가 무엇인지 알지 못했습니다. 수용을 사용자에게 위임했고, 이어서 `window.__DSH_BOOT__`가 없어 흰 화면인데도 맨 Vite HTTP 200을 성공으로 취급했으며, 마지막에는 원래 페이지가 이미 재빌드 산출물을 반영한 상태에서 다른 포트의 대체 `dsh web` 서버를 검증했습니다. 수정은 현재 URL과 런타임 모드를 모델이 보고 셸에서 조회할 수 있게 하고, listen 전에 독립 Vite를 거부하며, 외부 상태에 대해 프로덕션 새로 고침과 개발 HMR을 검증합니다.

## 개요

세션은 포트 3081의 DeepSeek Harness 웹 GUI 안에서 실행되었고, 선택된 워크스페이스는 빈 `test/` 디렉터리였습니다. 모델 요청에는 GUI도, 그 소스 체크아웃·URL·프로세스·업데이트 모드도 명시되지 않았습니다. 저장소 편의 기능은 Vite 개발 스크립트가 있는 `apps/web`을 노출했지만, 전체 브라우저 구성은 `dsh web` 뒤에 있었습니다.

결과 행동들은 개별적으로는 그럴듯했지만 하나의 수용 대상을 공유하지 않았습니다. 소스 편집, 성공한 빌드, HTTP 200, 주입된 부트 매니페스트, 사용자의 기존 페이지가 서로 대체 가능한 사실로 취급되었습니다.

증거 출처는 `session-3eb796c2-5159-4686-affe-df8719f6f987`의 영속 이벤트 로그이며, 그 헤더는 cwd `/Users/tn.shen/Documents/deepseek-harness-gui-master/test`를 기록합니다. 초기 요청 헤더는 시퀀스 6이고, 사용자 대상 핸드오프, 맨 Vite 실행, 대체 호스트 실행, 부트 매니페스트 프로브, 첫 3081 프로세스 프로브는 각각 시퀀스 30939, 31865, 34309, 34441, 34681입니다. 아래 타임라인은 이후 보고서에서 의도를 재구성하지 않고 그 이벤트를 따릅니다.

## 영향

사용자는 세 번의 연속 실수를 직접 찾아내야 했습니다. 수용이 사용자에게 되돌려졌고, 제안된 미리보기는 빈 페이지였고, 보고된 성공 URL은 사용자가 쓰던 페이지가 아니었습니다. 관리되지 않는 대체 서버도 사용자가 이의를 제기할 때까지 턴이 지나서도 살아 있었습니다.

이 조사에서 어떤 변경도 읽기 전용 3081·3082 시험 서비스를 재시작하거나 수정하지 않았습니다.

## 타임라인

- 턴 2에서 테마를 편집한 뒤 에이전트의 시퀀스-30939 메시지는 사용자에게 `pnpm run demo:tui`를 실행하거나 명시되지 않은 웹 애플리케이션을 열라고 했습니다. 조립된 웹 수용은 수행하지 않았습니다.
- 턴 3에서 에이전트는 `apps/web/package.json`을 읽고 시퀀스 31865에서 포트 5173에 맨 Vite를 실행했고, HTTP 200을 관찰하고 성공을 선언했습니다. 브라우저는 대신 `client-modules: window.__DSH_BOOT__ is missing or not an object`를 던지고 흰 페이지를 렌더링했습니다.
- 턴 4에서 에이전트는 전체 `dsh web` 경로를 찾고 셸을 재빌드하고 시퀀스 34309에서 포트 3334에 관리되지 않는 프로세스를 실행했으며, 시퀀스 34441에서 그 대체 서버가 부트 매니페스트와 함께 200을 반환하는지만 확인했습니다. 포트 3081은 한 번도 프로브하지 않았습니다.
- 턴 5에서 사용자는 시퀀스 34556에서 3081이 이미 새 테마를 보여 준다고 보고했습니다. 그제야 시퀀스 34681에서 에이전트가 기존 프로세스를 점검하고 중복 서버를 제거했습니다.

## 근본 원인

웹 어셈블리에는 현재 GUI, 정규 URL, 런타임 모드에 대한 모델 가시 식별자가 없었습니다. 세션 cwd는 사용자가 선택한 워크스페이스를 올바르게 식별했지만, 모델은 그 프로젝트 디렉터리를 애플리케이션 디렉터리로 취급했습니다. GUI 소스 체크아웃, 빌드 산출물, 서빙 프로세스, 대상 오리진, 브라우저 수용을 연결하는 영속 기록이 없었습니다.

잘못된 시작 경로가 그럴듯해 보인 이유는 맨 Vite가 HTTP 200을 반환했기 때문입니다. `window.__DSH_BOOT__`는 전체 호스트만 주입하므로 전송 준비가 애플리케이션 준비를 의미하지 않았습니다. 첫 회귀 테스트는 이 실수를 다른 형태로 반복했습니다. 타임아웃이 Vite를 죽이고 비제로 종료 단언을 만족시킨 것입니다. 실제 재현이 그 거짓 양성을 드러냈습니다.

백그라운드 프로세스 의미도 셸 `&`로 우회되어 작업 식별, 완료 알림, 수집, 정리가 적용되지 않았습니다. 따라서 포트 3334 검증은 두 번째 서비스가 동작한다는 것만 증명했습니다.

## 추가한 가드레일

- 웹 런처는 로그에 기록된 `app:web-surface` 프롬프트 섹션과 관리되는 `$DSH_WEB_URL` 환경에 정규 루프백 URL을 게시합니다.
- 프로덕션 지침은 산출물을 재빌드하고 새로 고침 후 기존 URL을 검증할 것을 요구합니다. 개발 지침은 HMR 수신기가 항상 켜져 있음을 설명합니다. 같은 체크아웃에서 `pnpm run dev:web`은 새로 고침 없는 리로드를 위해 클라이언트 플러그인 번들을 재빌드하지만, 셸과 일반 패키지 변경에는 여전히 새로 고침이 필요합니다.
- `apps/web`의 독립 Vite 서브 모드는 구성 중에 거부됩니다. 그 서브프로세스 테스트는 자연 종료를 증명하고 `Server.listen()`을 계측해 일시적 바인드가 모르는 채 통과하지 못하게 합니다.
- 계층화된 실제 경로 테스트가 CLI 요청, 정확한 프로덕션/개발 프롬프트, 셸 런타임 사실, 같은 포트의 정적 교체, 소스 워처 재빌드, 호스트 stat 폴링, 페이지 동일성이 유지된 상태의 브라우저 HMR을 다룹니다.
- PR 증거는 원래 3081 세션의 스크린샷과 실제 모델의 before/after GUI 실행을 보존합니다. 외부 브라우저, HTTP, 프로세스, 세션 로그 관찰이 수용을 뒷받침합니다.

## 교훈

- 에이전트는 사용자를 안내하기 전에 숨은 런타임 전제를 알아야 합니다. 시작 모드는 애플리케이션 컨텍스트이지 암묵적 지식이 아닙니다.
- HTTP 준비, 빌드 성공, 부트 매니페스트는 서로 다른 사실입니다. 수용은 정확한 오리진을 명시하고 그곳에서 요청된 변경을 외부에서 관찰합니다.
- 대체 서비스는 기존 페이지가 바뀌었다는 것을 증명할 수 없습니다. 장시간 실행 프로세스는 실제로 요청될 때 관리되는 작업 수명 주기를 사용합니다.
- 회귀 테스트는 보고된 메커니즘 때문에 실패할 수 있어야 합니다. 프로세스 타임아웃은 fail-fast와 같지 않고, 종료 후 포트 가용성은 포트가 한 번도 바인드되지 않았음을 증명하지 않습니다.
