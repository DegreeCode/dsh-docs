# 네트워크 프록시 뒤에서 DSH 실행하기

[English](network-proxy.md) | [中文](network-proxy.zh.md) | 한국어

DSH는 외부로 나가는 요청 — 모델 호출, 웹 검색, 페이지 가져오기, HTTP를 통한 MCP 서버 — 을 표준 프록시 환경 변수가 지정한 프록시로 라우팅합니다. 이 변수들은 시작할 때 읽으며 그 밖의 구성은 필요 없습니다. 몇몇 경로는 설계상 또는 런타임 한계로 직접 연결을 유지하며, 아래 "직접 연결로 남는 것"에 나열합니다.

## 변수 내보내기

```sh
export HTTPS_PROXY=http://127.0.0.1:7890
export HTTP_PROXY=http://127.0.0.1:7890
```

두 줄을 셸 프로필에 넣어 모든 `dsh` 실행이 이를 상속하게 하거나, API key 옆의 `$DSH_HOME/.env`(기본값 `~/.dsh/.env`)에 넣으세요. 내보낸 변수는 항상 그 파일보다 우선합니다. 프로젝트 자체의 `.env`로는 설정할 수 없습니다. 보안상 저장소가 임의로 트래픽 경로를 결정하지 못하도록 DSH는 프로젝트 내 `.env`의 프록시 설정을 허용하지 않고 시작을 거부합니다.

자격 증명이 필요한 프록시는 URL에 자격 증명을 담습니다: `http://user:password@proxy.example:8080`. DSH는 이 URL을 절대 다시 출력하지 않습니다. 진단 메시지는 거부한 변수 이름만 밝히므로 사용자 이름과 비밀번호 모두 어디에도 나타나지 않습니다.

## 브라우저는 프록시를 타는데 터미널은 타지 않는 이유

가장 혼동하기 쉬운 부분이며, DSH뿐만 아니라 터미널 도구 전반에서 흔히 나타나는 문제입니다. 모든 소프트웨어가 공통으로 따르는 단일 "시스템 프록시"는 존재하지 않으며, 서로 무관한 세 가지 메커니즘이 있습니다:

| 메커니즘 | 따르는 대상 |
|---|---|
| 운영체제의 프록시 설정 | Safari, 대부분의 macOS 네이티브 앱, Chrome, Edge |
| `HTTP_PROXY` / `HTTPS_PROXY` 환경 변수 | `curl`, `git`, `npm`, `pip`, DSH |
| TUN 모드(가상 네트워크 인터페이스) | 모든 프로그램, 투명하게 |

Clash 같은 프록시 클라이언트의 "시스템 프록시" 스위치는 첫 번째(OS 설정)만 변경합니다. 브라우저는 이를 참조하지만 일반 명령줄 도구는 감지하지 못합니다. 따라서 터미널 환경 변수를 별도로 내보내야(export) 하며, TUN 모드를 켜면 환경 변수 설정 없이도 두 환경 모두 투명하게 프록시를 통과합니다.

DSH는 운영체제의 프록시 설정을 읽지 않습니다. 변수를 내보내거나 TUN 모드를 사용하세요.

## 직접 연결로 둘 대상 선택하기

`NO_PROXY`는 직접 연결할 호스트를 나열합니다:

```sh
export NO_PROXY=internal.example.com,.corp.example.com,registry.local
```

항목은 호스트를 지정하며 그 아래 모든 하위 도메인과 함께 일치합니다. `NO_PROXY=example.com`이면 `api.example.com`도 직접 연결됩니다. 앞의 `.` 또는 `*.`도 허용되며 같은 의미입니다. 항목에는 `:port`를 붙일 수 있고, `*`는 모두 우회합니다.

**CIDR 범위는 동작하지 않습니다.** 운영체제의 우회 목록에는 `10.0.0.0/8` 또는 `192.168.0.0/16` 같은 항목이 흔히 있습니다. 이를 `NO_PROXY`에 복사해도 효과가 없습니다. 대신 호스트 이름이나 도메인 접미사를 사용하세요.

`localhost`나 `127.0.0.1`을 나열할 필요는 없습니다. DSH는 항상 loopback을 우회합니다. 그렇지 않으면 자체 웹 UI와 로컬 서버가 프록시를 거쳐 루프를 돌기 때문입니다.

## 알아 둘 만한 제한

**SOCKS 프록시는 지원하지 않습니다.** `socks5://` 값은 시작 시 경고와 함께 건너뛰며, DSH는 해당 스킴에 대해 직접 연결을 시도합니다. `HTTPS_PROXY=socks5://…`를 유효한 `HTTP_PROXY`와 함께 설정하면 `https:` 요청은 HTTP 프록시를 경유하지 않고 직접 연결로 남습니다. 프록시 애플리케이션의 HTTP 포트를 환경 변수로 지정하세요. 대부분의 도구는 두 방식을 모두 제공하며 HTTP 포트는 보통 SOCKS 포트와 인접해 있습니다.

**`ALL_PROXY`도 대체 경로로 지원됩니다.** Node와 curl 사이에 동작 차이가 있더라도 DSH는 두 프로토콜 모두에서 `ALL_PROXY`를 대체 경로로 인식합니다. 하지만 설정의 명확성을 위해 `HTTPS_PROXY`를 명시하는 편이 권장됩니다.

**TLS를 가로채는 기업 프록시에는 그 인증서가 필요합니다.** 프록시에 도달한 뒤 요청이 인증서 오류로 실패하면, 실행 전에 Node가 조직의 CA 번들을 가리키게 하세요:

```sh
export NODE_EXTRA_CA_CERTS=/path/to/corporate-ca.pem
```

Node는 이 변수를 프로세스 시작 시에만 읽으므로 `dsh`를 실행하기 전에 내보내세요.

**DSH가 대신 실행하는 도구도 같은 프록시를 따릅니다.** bash 도구의 명령, `git`, `gh`, 그리고 자식 프로세스로 시작된 MCP 서버는 모두 이 변수를 상속합니다. 자식 Node 프로그램은 자체 설치된 런타임을 사용합니다. Node 22.21+와 Node 24+는 이 변수를 따르고, 더 오래된 런타임은 직접 연결합니다. 프록시 변수 중 하나에 DSH가 거부한 값(예: SOCKS URL)이 있으면 Node 기반 도구도 시작에 실패하지 않고 직접 연결하며, `curl`과 `git`은 여전히 그 값을 읽습니다.

**프록시 URL의 비밀번호도 그 도구들에 전달됩니다.** `HTTPS_PROXY=http://alice:s3cret@proxy.example:8080`는 평범한 환경 변수이므로 DSH가 실행하는 모든 명령(모델이 작성한 명령 포함)이 이를 읽을 수 있고, 환경을 출력하는 명령은 비밀번호를 보존되는 출력에 남깁니다. 이는 셸의 다른 모든 프로그램에서 이미 그렇게 동작하는 방식입니다. 이것이 문제라면 프록시에 자격 증명이 필요 없는 진입점을 두거나 URL 대신 다른 방식으로 인증하세요.

## 직접 연결로 남는 것

DSH가 보내는 모든 요청이 프록시를 거치는 것은 아닙니다:

- **로컬 머신 통신.** 루프백(loopback)은 항상 직접 연결됩니다: `localhost`, 전체 `127.0.0.0/8` 대역, `::1`, `0.0.0.0`. 프록시는 로컬에서만 리스닝하는 서비스에 정상적으로 도달할 수 없기 때문입니다.
- **모델이 작성한 코드.** 워크플로 워커와 Node ptc-runtime 프로세스는 환경 프록시 설정을 주입받지 않으므로, 모델이 작성한 스크립트가 비밀번호가 포함될 수 있는 프록시 URL을 무단으로 읽을 수 없습니다. 직접 네트워크 요청을 실행하는 코드는 필요한 프록시를 자체적으로 구성해야 하며, 실행 샌드박스 정책의 적용을 받습니다.
- **사용량 텔레메트리.** OTLP 익스포터는 프록시 클라이언트가 아니라 Node 기본 HTTP 클라이언트를 사용하므로, 텔레메트리는 직접 연결을 시도하며 외부 직접 연결이 차단된 폐쇄망 환경에서는 전송이 조용히 실패합니다. DSH의 핵심 기능은 이에 의존하지 않으므로 문제없이 작동합니다. 완전히 끄려면 `DSH_TELEMETRY_MODE=DISABLED`를 설정하세요.
- **리터럴 사설 주소로의 `web_fetch`.** `http://10.0.0.5/` 같은 주소를 지정한 URL은 프록시로 넘기지 않고 거부되며, 프록시를 구성하지 않았을 때와 같은 거부입니다.

## 동작 확인

에이전트에게 페이지를 가져오게 하고 프록시 애플리케이션의 연결 로그를 보세요:

```sh
dsh --profile headless "fetch https://example.com and tell me the page title"
```

요청이 로그에 나타나지 않으면 변수가 DSH 자체 환경까지 유지되는지 확인하세요:

```sh
env | grep -i proxy
```
