# Cordis 입문서

[English](cordis-primer.md) | [中文](cordis-primer.zh.md) | 한국어

Cordis는 DeepSeek Harness의 기반이 되는 내장(vendored) 플러그인 프레임워크입니다. 이 입문서는 플러그인 개발자가 [하위 시스템 페이지](subsystems/core.ko.md)에서 생성된 서비스 및 이벤트 참조 문서를 읽기 전에 꼭 알아두어야 할 Cordis의 핵심 개념을 설명합니다. 직접 실습하며 학습하고 싶다면 [Cordis 자습서](cordis-tutorial/index.ko.md)를 참고하세요. 내장된 소스 코드와 동기화 절차는 [vendor/README.md](../vendor/README.md)에 정리되어 있습니다.

## 5가지 핵심 개념으로 보는 Cordis

- **플러그인은 서비스를 구현하는 객체입니다.** 선택적인 `inject` 및 `apply(ctx)` 프로퍼티를 가진 함수 형태일 수도 있고, 수명 주기를 Cordis가 현재 컨텍스트에 마운트하는 `Service` 서브클래스 형태일 수도 있습니다.
- **컨텍스트는 서비스 저장소입니다.** 각 서비스는 컨텍스트 내에서 `ctx.tools`, `ctx.llm`, `ctx.sessions`와 같이 고유하고 안정적인 `ctx.<key>`를 점유하며, 다른 플러그인은 구체적인 구현 클래스를 직접 import하는 대신 키를 통해 서비스를 조회합니다.
- **`inject`로 서비스 의존성을 선언합니다.** 필요한 서비스를 선언한 플러그인은 해당 서비스가 준비될 때까지 대기하므로, 수동으로 부팅 순서를 맞출 필요 없이 의존성 요구사항 선언만으로 로드 순서가 자연스럽게 결정됩니다.
- **통신에는 타입 안전한 이벤트를 사용합니다.** 서비스는 TypeScript 선언 병합(declaration merging)으로 이벤트 이름을 선언한 뒤, 리스너의 관찰, 래핑, 팬아웃, 순차 실행, 또는 첫 번째 bail 값에서의 중단 여부에 따라 `emit`, `waterfall`, `parallel`, `serial`, `bail` 방식으로 디스패치합니다.
- **등록은 되돌릴 수 있는 효과(effect)입니다.** 프롬프트 섹션, 도구 스키마, 어댑터, 제공자, 이벤트 리스너 등은 모두 `ctx.effect()`나 `ctx.on()`을 통해 설치되므로, 플러그인 리로드나 정리(teardown) 시 예측 가능하게 자동 해제(롤백)됩니다.

## 디스패치 모드

모든 이벤트는 다음 디스패치 모드 중 하나를 가지며, 지정된 전용 메서드로만 디스패치할 수 있습니다:

| 모드 | await 지원 | 디스패치 순서 | 반환값 유무 |
|---|---|---|---|
| `emit` | 아니요 | 리스너가 등록 순서대로 관찰합니다 | 없음 |
| `waterfall` | 아니요 | 리스너가 등록 순서대로 관찰합니다 | 있음 |
| `parallel` | 예 | 모든 리스너가 이벤트를 병렬로 관찰합니다 | 없음 |
| `serial` | 예 | 리스너가 등록 순서대로 관찰합니다 | 있음 |
| `bail` | 아니요 | 리스너가 등록 순서대로 실행되며, 하나라도 유효한 값을 반환(bail)하면 즉시 중단합니다 | 있음 |

디스패치 모드는 이벤트의 공개 계약의 일부입니다. 새로 추가되는 하네스 이벤트는 `@mode` 태그로 이를 명시하므로, 생성된 카탈로그가 선언과 디스패치 지점의 정합성을 검증할 수 있습니다.

## Cordis Waterfall 동작 원리

`ctx.waterfall`은 둘러싸는(around) 형태의 미들웨어입니다. 리스너는 `(...args, next)`를 인자로 받습니다. `next()`를 호출하면 (필요시 수정한) 결과를 다음 서비스로 위임하고, `next()`를 호출하지 않고 반환하면 이후 실행을 즉시 중단(단락)합니다. 값은 `next()`의 반환값을 통해 다음 단계로 전달됩니다.

협력적인 리스너는 보통 공유된 요청이나 결정 객체를 수정한 뒤 `next()`를 호출하여 위임합니다. 리스너가 결과를 완전히 대체할 수도 있으며, 이 경우 다운스트림 리스너는 대체된 이후의 결과만 보게 됩니다. `prepend: true`는 해당 리스너가 일반 등록 항목보다 반드시 먼저 실행되어야 할 때만 제한적으로 사용합니다.

단일 결정을 다루는 이벤트에서는 이러한 단락(조기 종료) 처리가 설계상의 정상 동작입니다. 정책 리스너가 최종 결정을 내릴 권한을 가질 때는 `next()` 없이 즉시 반환할 수 있지만, 부가 정보만 덧붙이거나 관찰만 하는 리스너는 반드시 `next()`로 위임해야 합니다.

## 로더 구성

`@deepseek-ai/cordis-plugin-include`는 `!!js` 구문을 표현식 노드로 파싱합니다. 로더(Loader)는 선언된 주입 서비스가 활성화된 후 플러그인 컨텍스트(`ctx.serviceName`)를 기준으로 각 항목의 `config`를 평가(치환)하고, 마운트 결정 시점마다 로더 컨텍스트를 기준으로 `disabled` 필드를 평가합니다. Include 플러그인은 대상이 활성화될 때까지 중첩된 행 표현식을 그대로 보존합니다. 그 외의 항목 메타데이터는 리터럴 값으로 유지됩니다. 실행 환경에 따라 플러그인을 조건부 선택해야 한다면 구성 오버레이를 사용하세요.

## 실전 개발 규칙

동작 로직은 항상 플러그인 단위로 캡슐화하세요. 도구 파이프라인 이벤트는 `ctx.tools`, 모델 스트리밍은 `ctx.llm`, 실시간 에이전트 조율은 `ctx.agents`에 속합니다. 동작을 가로채거나 정책을 적용할 때는 이벤트를 활용하고, 기능을 직접 호출할 때는 서비스 메서드를 사용하는 것이 좋습니다.

모든 등록 작업에는 정리(disposer) 함수가 수반되어야 합니다. `ctx.effect()`에서 정리 함수를 직접 반환하거나, 이를 대신 처리해 주는 Cordis 헬퍼 함수를 활용하세요. 리소스 해제 순서가 중요하다면 관련 작업들을 하나의 effect로 묶어서 의도한 역순으로 안전하게 정리되도록 구성하세요.
