# 테스트 정책

[English](testing.md) | [中文](testing.zh.md) | 한국어

이 저장소의 계층별 테스트 전략과 테스트 스위트가 통과(초록색) 상태를 의미 있게 유지하도록 하는 규칙을 설명합니다. 실행 명령어는 루트 [AGENTS.md](../AGENTS.md)에 있으며, 세부 설계 근거는 연결된 각 Agent Note에 기술되어 있습니다.

## 테스트 계층

- **단위 테스트**(`pnpm run test`): 각 패키지 및 예제의 `tests/**` 디렉터리에 있는 spec 파일과 `scripts/**/*.spec.ts`에 해당하는 저장소 스크립트 spec에 대해 vitest를 실행합니다. 테스트 코드는 자신이 검증하는 소스 코드 영역 바로 곁에 둡니다. 모든 레지스트리 구현에는 HMR(핫 모듈 대체) 안정성 테스트가 포함되어야 합니다(기여 fiber를 폐기(dispose)한 후 리소스 정리를 단언). 경계 조건, 오류 처리 경로, 이벤트 발생 순서, 동시성 경쟁 상태, 계약 회귀 테스트를 상시 우선적으로 작성하세요(`packages/core/agent-loop/tests/contract-regressions.spec.ts` 참고).
- **커버리지 게이트**(`pnpm run test:coverage`): CI 필수 게이트이며 `packages/*/*/src`의 모든 파일에 대해 파일별 100% 라인 커버리지를 요구합니다. 커버되지 않는 라인이 있다면 대개 추가해야 할 테스트가 누락된 것이 아니라 게이트가 삭제 대상으로 감지한 불필요한 죽은 코드(dead code)인 경우가 많습니다. 라인 커버리지는 필요조건일 뿐 결코 충분조건이 아닙니다. 해당 라인이 실행되었다는 사실만 증명할 뿐, 기능이 출시 사양대로 올바르게 동작함을 보장하지는 않습니다. `packages/shell/pwsh-local/src`의 파일별 100% 커버리지를 달성하려면 실제 `pwsh`가 필요합니다. 로컬에 pwsh가 없으면 테스트 스위트가 자동으로 건너뛰고 `vitest.config.ts`가 해당 파일을 예외 처리하여 개발자 환경에서도 초록색을 유지할 수 있지만, CI 러너에는 pwsh가 설치되어 있으므로 100% 기준이 엄격히 적용됩니다.
- **실제 API e2e**(`pnpm run test:e2e`): API 키가 설정되어 있을 때 실제 제공자 API 엔드포인트를 상대로 실행하는 엔드투엔드 테스트입니다. DeepSeek 모델 및 자체 키로 게이팅되는 각 제공자별 스모크 테스트(`EXA_API_KEY`, `PERPLEXITY_API_KEY`, …)를 포함합니다. 키가 설정되어 있지 않으면 각 테스트 스위트가 자동으로 실행을 건너뛰므로 키가 없는 CI 환경에서도 안전하게 초록색 통과 상태를 유지합니다 ([실제 API e2e Agent Note](../.agents/notes/implemented/testing/2026-06-19-real-api-e2e-ci.md)).
- **소유자 로컬 기대 출력 테스트**(`pnpm run test:expected`): 기록된 세션 전체 왕복 없이 조립된 CLI 및 프로세스 기대 출력을 외부 키 없이 가볍게 검증합니다. 테스트 드라이버는 `tests/expected/` 옆의 `*.expected.e2e.ts` 파일을 사용하며, CI에서는 빌드된 export를 직접 실행합니다. 패키지 및 스크립트 기대값은 `test`, 브라우저 화면 기대값은 `test:web` 명령어로 검증합니다.
- **성능 벤치마크**(`pnpm run test:bench`, 필수 Linux PR 게이트 `node 24 / benchmarks`): `benchmarks/` 디렉터리에 사용자 핵심 경로 게이트들이 모여 있습니다. 라이브러리와 워커를 빌드한 후, 성능 측정 코드는 TSX가 아닌 일반 Node.js 프로세스에서 실행됩니다. 합성 입력 데이터를 통해 실행 시간, 힙 메모리, 확장성 예산을 강제 검증하며, 패키지 로컬의 `.perf.ts` 파일은 로컬 진단용으로 유지됩니다 ([벤치마크 규칙](../.agents/notes/implemented/testing/2026-09-04-session-open-performance-gate.md)).
- **스냅샷 테스트**(`pnpm run test:snapshot`): 상위 시나리오에서 가장 최신의 기록 세대 파일이 사용자 입력 및 모델 재생 데이터를 제공하고, 기대되는 최종 영속화 결과 역할을 수행합니다. 부모 세션 파일명은 `session[.vN].jsonl`이고 자식 세션 역할은 `session.<ordinal>[.vN].jsonl` 형태를 취합니다. v0 버전은 `.v0` 표기를 생략하며, 양수 버전은 소문자 `.vN` 표기가 필요하고 각 파일명은 내부 헤더와 일치해야 합니다. 프로세스 시나리오는 `dsh` 명령어로 시작합니다. headless는 일회성 실행 동작을, SDK는 영속 제어를, ACP는 자동화 프로토콜 동작을 검증하며, Web은 동일 세션 곁에 브라우저/ARIA 접근성 증거 데이터를 함께 보존합니다. `snapshot.yml`은 프로필, 구성/헤더 클래스, 기록 정책, 예외적 재생 또는 입력 메타데이터, 워크스페이스 상태를 선언합니다. 타입 안전한 토큰이 부모/자식 식별 관계를 보존하며, 헤더 pin만이 프롬프트/스키마 사이드카를 소유합니다. 파일 변경을 수반하는 시나리오는 전체 `workspace.expected/` 트리를 독립적으로 비교하며, 일반 record나 refresh 명령어는 이 트리를 덮어쓰지 않습니다. 모델 응답 텍스트(트랜스크립트)가 변경된 경우 `test:snapshot:record`를, 재생 입력 데이터가 여전히 유효한 경우에는 `test:snapshot:refresh`를 사용하고 생성된 diff를 꼼꼼히 검토하세요.
- **웹 브라우저 스냅샷**(`pnpm run test:web`, 필수 Linux PR 게이트): 플러그인 CSS를 빌드한 후 Chromium 브라우저 환경에서 세션 기반 `snapshots/web/` 출력과 UI 전용 `apps/web/tests/expected/` 출력을 모두 시각적으로 비교 검증합니다. 모델 및 추론 선택기 관련 시나리오는 WebKit 브라우저에서도 함께 실행됩니다. CI 환경에서는 읽기 전용 모드인 `DSH_SNAPSHOT=replay`를 강제 적용하며, record 및 refresh는 로컬 환경에서만 실행하고 모든 diff를 철저히 검토해야 합니다 ([웹 레인](../.agents/notes/implemented/testing/2026-07-24-web-gui-browser-e2e-lane.md), [CI 참조](../scripts/run-web-snapshots.ts)).

세션 픽스처는 헤더와 페이로드를 그대로 보존하지만 본문의 seq/time 엔벨로프는 생략하며, 세션 재생기가 이를 동적으로 합성합니다. 재생, 기록, 새로고침 시에는 각 부모/자식 역할의 가장 최신 세대 파일을 선택합니다. 최신 픽스처는 파일명과 헤더에 [기록 형식](session-format-status.ko.md)을 준수하고, 이벤트마다 한 줄씩 작성하며, 압축된 Assistant 스트림을 내장합니다. 과거 버전 픽스처는 공개 배포 당시의 표현을 그대로 유지하여, 명시적인 `sessionFormat` 검증기가 마이그레이션 커버리지를 지속적으로 보존할 수 있도록 합니다. 기존 세대를 변경하지 않고 후속 세대를 안전하게 추가하려면 [형식 버전 가이드](cookbook/adding-a-session-format-version.ko.md#snapshot-successors)를 참고하세요.

## Spec 파일 실행 방식

포크된 테스트 워커들은 여러 spec 파일을 병렬로 동시에 실행하며, 커버리지 게이트는 동일한 작업 내의 다른 게이트들과 나란히 [동시 파티션](../scripts/coverage-partitions.ts)으로 분할 실행되고, 셀프 호스팅 러너는 단일 호스트와 단일 볼륨을 공유합니다. 격리되는 것은 오직 개별 프로세스뿐입니다. 네트워크 포트, 고정된 파일 경로, 외부 네임스페이스, 상속된 자식 프로세스는 자동으로 격리되지 않습니다. 따라서 테스트 중에 획득한 모든 리소스는 teardown 단계에서 반드시 안전하게 해제해야 합니다. 단독으로 실행할 때만 통과하는 spec은 러너의 문제가 아니라 테스트 코드 자체의 결함입니다. [dsh-ci-test-reliability](../.agents/skills/dsh-ci-test-reliability/SKILL.md) 가이드에서 리소스 할당, 복구, 동기화, 타임아웃 예산, 플랫폼별 처리, teardown 규칙을 규정하며, [간헐적 실패(flake) 진단 워크플로](../.agents/skills/dsh-ci-test-reliability/references/ci-flake-diagnosis.md)를 통해 비결정적 실패를 체계적으로 분류합니다. [예기치 않은 fork 프로세스 종료](../scripts/coverage-fork-diagnostics.ts) 발생 시 PID, 파일명, 종료 코드, 시그널 정보를 상세히 보고합니다.

## API 키 사용 정책: 우리는 DeepSeek입니다

우리는 DeepSeek입니다. 실제 API 테스트를 아끼지 마세요. API 키 없는 테스트는 내부 배관(파이프라인)이 연결되어 있음을 증명할 뿐이며, 실제 키를 사용한 실행만이 에이전트가 실제 모델을 상대로 올바르게 동작함을 증명합니다. 파일 쓰기 프롬프트, 다중 턴 대화, 도구 실행, 스트림 중간 취소 등의 실제 시나리오를 적극적으로 다루세요. 가장 가치 있는 테스트는 배포 대상인 `dsh` 프로필을 실제로 부팅하고 프롬프트 하나를 전송한 뒤 외부 환경의 변화를 확인하는 **스모크 테스트**입니다. 이는 mock 테스트로는 절대 잡아낼 수 없는 "단위 테스트는 통과하지만 실제 제품은 고장 나는" 치명적인 결함을 사전에 잡아냅니다 ([포스트모템 0001](postmortem/0001-acp-default-export-drops-inject.ko.md) 참고). 키가 없을 때의 자동 건너뛰기 기능은 시크릿이 설정되지 않은 CI 환경과 키가 없는 일반 기여자의 작업을 막지 않기 위한 배려일 뿐, 비용 절감을 위한 신호가 아닙니다. 프로필 수준의 통합 테스트는 `apps/cli/tests/profiles/` 아래에 있으며, 패키지별 구성 테스트는 해당 패키지의 테스트 디렉터리에 함께 둡니다.

## Mock보다 실제 구현체 사용을 선호합니다

비용이 크거나 비결정적인 외부 경계(LLM 어댑터, 실제 네트워크 I/O, 시스템 시계)만 선별적으로 mock하고, 그 하위의 모든 컴포넌트는 실제 구현체를 유지하세요. 인위적으로 만든 mock 대체물은 브리지 계층이 바이트 데이터를 전달할 수 있다는 것만 증명할 뿐, 실제 출시되는 도구가 명세대로 동작하는지는 증명하지 못합니다. 브리지 도구 호출 테스트는 스크립트 기반의 mock 모델 뒤에 실제 도구 레지스트리와 실행 파이프라인을 그대로 유지해야 합니다. `makeBridgeHarness()`는 에이전트 루프, 세션 저장소, 도구 레지스트리, JSONL 영속성을 모두 온전히 마운트하고 오직 `MockAdapter`만을 유일한 mock으로 사용합니다 (`packages/acp/acp/tests/harness.ts` 참고).

복구 메커니즘 테스트는 청크 수신 전/후의 실패를 단계별로 구분하여, 실패한 청크가 잘못된 메시지나 도구 부수 효과를 남기지 않음을 명확히 증명해야 합니다. 리소스 소진, 취소 처리, 정책 구성, 영속성 저장, 상태 전이, 네트워크 호출 횟수, 유휴 타임아웃에 따른 연결 종료, 그리고 실제 출시되는 Loader 구성을 충실히 검증하세요.

## 에이전트의 자체 보고가 아닌 실제 환경의 변화를 검증합니다

e2e 테스트의 단언(assertion)은 명령을 다시 실행해 보거나 변경된 파일을 외부에서 직접 다시 읽어 검증해야 합니다. 에이전트가 출력한 응답 텍스트 내의 키워드를 검사하는 방식은, 실제로는 실패했으면서 성공했다고 거짓 보고하는 에이전트를 걸러내지 못합니다. 수정되지 않아야 하는 파일은 바이트 단위까지 이전과 완전히 동일함을 엄격히 단언하세요. e2e 테스트는 자신이 생성한 리소스의 전체 수명 주기를 직접 책임져야 합니다. 테스트 내부에서 리소스를 생성하고, 테스트 실패, 재시도, 타임아웃이 발생하더라도 `afterEach` 훅에서 안전하게 폐기(dispose)하세요. 공유 픽스처는 다른 `*.e2e.ts` 파일이 아니라 평범한 헬퍼 파일인 `tests/harness.ts`에 두어야 합니다 (spec 파일을 import하면 내부의 `describe` 블록이 중복 등록되어 실제 API 호출이 불필요하게 반복 실행됩니다).

## 실제 사용자 진입 경로를 검증합니다

- 실제 제품에 포함되는 플러그인은 단순 단위 테스트가 아닌, 실제 구성(REAL configuration) 기반의 통합 테스트가 반드시 필요합니다. 코드에서 수동으로 `ctx.plugin(...)`을 호출하는 것만으로는 부족합니다. 실제 Loader와 애플리케이션 프로세스를 통해 테스트 전용 `cordis.yml`을 부팅하고, 외부 서비스나 비결정적 입력만 mock 처리한 뒤, 모델이 보게 되는 요청 및 로그, 영속화된 상태, 또는 사용자가 보게 되는 최종 출력을 엄격히 단언하세요. 선택적 옵트인 설정을 출시 기본값으로 가정하고 테스트하지 마세요.
- 보호 검증(guard)은 회귀 결함이 발생했을 때 실제로 실패해야만 진정한 보호 검증입니다. `inject` 선언이 없는 번들/구성 플러그인의 경우, 필수적인 named export 대신 default export가 잘못 사용되더라도 Loader 스모크 테스트가 그대로 통과해 버리는 문제가 있었습니다. 명시적인 `expect('default' in mod).toBe(false)` 검증과 `unwrapExports` 왕복 단언을 추가하여 결함을 실제로 잡아낼 수 있음을 증명하세요. 일부러 결함을 유도하여 테스트가 빨간색(실패)으로 바뀌는 것을 확인한 후 다시 정상 코드로 되돌려야 합니다.
- "실제 진입 경로"란 최종 빌드되어 배포되는 아티팩트를 의미합니다. 패키지의 CLI `bin`은 일반 `node` 환경에서 빌드된 `lib/bin.js`를 실행하므로, tsx 환경이 가려버릴 수 있는 결함(프로미스 확정 경쟁 상태, 모듈 해석 오류, 삼켜진 로드 실패 등)을 투명하게 드러냅니다. 동일한 원칙이 index 이외의 런타임 진입점(Node 프로세스 부트스트랩인 `lib/process.js`)과 여러 번들이 공유하는 싱글턴 모듈(`packages/sdk/server/tests/built-scope-carrier.e2e.ts`)에도 적용됩니다. 빌드 아티팩트 스모크 테스트를 항상 통과 상태로 유지하고(`packages/examples/*/tests/built-bin.e2e.ts`, `packages/ptc-runtime/ptc-runtime-node/tests/built-lib.e2e.ts`), 필수 구성이 누락되었을 때 실제로 0이 아닌 종료 코드로 프로세스가 정상 종료되는지 단언하세요.

## 테스트 모듈 해석: 소스 평면 원칙

- 모든 vitest 구성은 vite-tsconfig-paths를 통해 `tsconfig.base.json`을 참조하도록 설정되어 있습니다. 워크스페이스 패키지의 베어(bare) import는 항상 `src` 디렉터리로 직접 해석되며([레이아웃 가이드](development.ko.md#typescript-프로젝트-레이아웃)), 패키지의 `exports` 필드를 거쳐 빌드된 `lib/` 경로로 해석되지 않습니다. 빌드 디렉터리에 오래된 아티팩트가 남아 있으면 모듈 싱글턴의 중복 인스턴스가 로드될 위험이 있기 때문입니다. 빌드된 아티팩트는 `lib` 모드 하위 프로세스나 빌드 스모크 테스트처럼 명시적으로 지정된 경우에만 사용됩니다.

## 테스트 하위 프로세스 실행 모드

- CI 및 빌드 산출물이 준비된 테스트 레인은 공유 이중 모드 런처를 사용하여 빌드된 `lib/` 디렉터리에서 프로필 및 Cordis 구성 하위 프로세스를 실행합니다. 이 하위 프로세스 명령어에 임의로 `--import tsx`를 직접 하드코딩하지 마세요.
- Cordis를 로드하지 않는 순수 프로토콜 및 운영체제 픽스처는 tsx나 루트 경로 맵 없이 Node.js를 통해 타입 제거(type stripping) 방식으로 `.ts` 파일을 직접 실행합니다.
- 테스트의 본래 목적이 소스 경로 해석 메커니즘 자체를 검증하는 것인 경우에만 예외적으로 `src` 실행을 선택할 수 있으며, 그 의도를 테스트 코드에 명시해야 합니다.

## 스냅샷 테스트 작성 기준

모델, 프로토콜, 사용자에게 노출되는 모든 비사소한(중요한) 변경 사항은 동일한 PR에서 API 키 없는 기록 세션 시나리오를 추가하거나 갱신해야 합니다. 개별 패키지 단위 테스트, e2e 테스트, mock 전용 테스트, 정적 증거 자료는 조립된 실제 대화 트랜스크립트를 완전히 대체할 수 없습니다. Headless, SDK, ACP, Web의 스냅샷 기록은 각각 `snapshots/session/`, `snapshots/sdk/`, `snapshots/acp/`, `snapshots/web/` 디렉터리에 보관됩니다. Web 렌더링 테스트는 다른 시나리오의 정규 세션 데이터를 명시적으로 공유하여 활용할 수 있습니다. 기록된 세션 기반이 아닌 단순 기대 출력값은 각 앱, 패키지, 스크립트 내부의 `tests/expected/` 디렉터리에 유지하며 `*.snapshot.ts` 접미사를 사용하지 않습니다. [`dsh-session-snapshot`](../packages/test-support/session-snapshot/README.md) 패키지가 공통 저장 규칙과 프로필 어댑터를 총괄 관리합니다. 에이전트 루프, 세션 수명 주기, `SessionEventMap`이 변경되면 TypeScript와 Python 두 SDK의 프로젝션을 모두 갱신해야 합니다 (`snapshots/sdk/`는 TypeScript 소유, `scripts/snapshots/python-sdk-single-exe/`는 [Python 런타임 CI](../.github/workflows/ci-master.yml) 소유). 새로운 기능 seam을 추가하거나 수명 주기 및 트랜스크립트 구조를 변경할 때는 설계 계획 단계에서 영향받는 모든 테스트 계층을 명확히 정의해야 합니다.
