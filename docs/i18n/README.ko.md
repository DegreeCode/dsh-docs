# 이중 언어 문서

[English](README.md) | [中文](README.zh.md) | 한국어

이 저장소의 문서는 회사 안팎의 사람과 에이전트가 읽으므로, 범위에 속한 모든 문서를 영어와 중국어 간체로 유지합니다. 독자용 안내서는 선택적인 한국어 렌더링을 함께 둘 수 있습니다. 이 페이지는 쌍 계약, 검사, 범위, 제외를 정의하고, [translation-rules.md](translation-rules.ko.md)는 번역 방법을 정의하며, [terminology.md](terminology.md)는 용어의 진실 공급원입니다. 일상적인 에이전트 작업은 [docs/AGENTS.md](../AGENTS.md)의 경량 경로를 따르며, 확장 [.agents/skills/dsh-translate-docs](../../.agents/skills/dsh-translate-docs/SKILL.md) 워크플로는 사용자가 명시적으로 호출할 때만 사용할 수 있습니다.

## 쌍 계약

- **두 언어는 동등한 권위를 가집니다.** 문서는 어느 언어로 먼저 작성하고 리뷰해도 됩니다. 중국어로 먼저 쓴 Agent Note도 영어로 먼저 쓴 것만큼 정당하며, 대응 문서는 그로부터 번역합니다. 어느 파일도 다른 쪽보다 우위에 있지 않고, 두 파일을 묶는 것은 같은 내용을 말해야 한다는 점입니다.
- **쌍은 형제 파일 세 개입니다.** 영어 `foo.md`, 중국어 `foo.zh.md`, 일관성 기록 `foo.i18n.yaml`이 모두 같은 디렉터리에 있습니다. 로케일 디렉터리도, 별도 번역 저장소도, 언어가 뒤섞인 이중 언어 파일도 없습니다. 쌍은 통째로 병합됩니다. PR이 다른 두 파일 없이 한 언어만 반영하는 일은 없습니다.
- **일관성 기록.** `foo.i18n.yaml`은 언어별 내용이 아직 남아 있는 제목 섹션마다 항목을 하나씩 가집니다. 키는 그 섹션의 영어 제목 슬러그 경로이며(`/`는 첫 제목 앞 텍스트, 경로가 반복되면 `~2`, `~3`, …), 항목은 그 섹션에서 양쪽이 다른 영어 블록과 중국어 블록의 해시를 담습니다:

  ```yaml
  /foo:
    en: 41d772192075e133
    zh: dda91c6c670cfd9d
  /foo/usage:
    en: 86940bea4a3c7ed6
    zh: de78429597783c7f
  ```

  한쪽의 섹션 `i`는 다른 쪽의 섹션 `i`에 대응합니다. 각 쪽의 해시는 펜스 코드 블록과 생성 영역, 즉 게이트가 이미 양쪽에서 동일해야 한다고 요구하는 두 종류의 내용을 제외한 그 섹션의 모든 최상위 블록을 포괄합니다. 우연히 동일한 내용도 여전히 해시에 포함됩니다. 남은 블록이 없는 섹션에는 항목이 없습니다. 영역을 다시 생성하거나 양쪽에서 코드 블록을 편집해도 기록은 바뀌지 않고, 서로 다른 섹션을 편집하면 서로 다른 기록 줄이 바뀌므로 Git의 기본 텍스트 병합(GitHub 포함)이 이를 합칩니다. 두 브랜치가 같은 섹션에서 해시 대상 내용을 바꾼 경우에만 기록이 충돌합니다. Markdown을 해결하고 쌍을 다시 기록하세요. 어긋난 쌍은 파일 전체를 다시 번역하지 않고, 편집된 쪽의 diff에 맞춰 대응 문서를 최소한으로 패치하여 갱신합니다. 게이트가 바뀐 섹션마다 이름을 알려 줍니다. 일상 작업은 그 패치를 직접 수행하고, 사용자가 확장 워크플로를 명시적으로 호출하면 `pnpm run gen-translation-brief <pair>`가 기록된 항목을 만들어 내는 최신 커밋에서 마지막으로 확인된 텍스트를 복구하고, 안전하게 정렬되는 가장 좁은 단위로 갱신을 조립하며, `--apply`는 구조 검증 후 코드 펜스만 바뀐 변경을 끼워 넣을 수 있습니다. 쌍을 다시 일치시킨 뒤 `pnpm run verify-translation-pairing --write <pair>`로 항목을 다시 기록합니다. 그 yaml diff가 일관성을 확인하는 리뷰 가능한 행위이며, 그래서 `--write`는 확인한 쌍의 이름을 요구합니다(`--write --all`은 코퍼스 전체를 대상으로 하는 명시적 형태입니다).

  중국어 파일은 영어 역링크를 유지해야 하고, 사람이 작성한 영어 원본은 중국어 링크를 유지해야 하지만, 생성된 영어 원본으로 목록에 오른 것은 예외입니다. [보관된 섹션 키 쌍 기록 Agent Note](../../.agents/notes/archived/process/2026-09-23-section-keyed-translation-pairing-records.md)가 형식 선택과 그 대안을 기록합니다.
- **선택적 한국어 렌더링.** 어떤 쌍이든 세 계약 파일 옆에 한국어 `foo.ko.md`를 함께 둘 수 있습니다(MAY). 한국어는 선택적인 세 번째 렌더링입니다. 일관성 기록이 없고, 존재할 의무도 없으며, 두 쪽이 어긋날 때 영어 원본이 계속 권위 있습니다. 한국어 파일은 H1 제목 바로 다음에 `[English](foo.md) | [中文](foo.zh.md) | 한국어`로 시작하며, 한국어 렌더링을 제공하는 영어나 중국어 쪽은 표준 전환 줄 끝에 `| [한국어](foo.ko.md)`를 덧붙입니다. 한국어 파일은 이중 언어 코퍼스 밖에 있으므로 쌍 게이트는 이를 무시하지만, 일반 Markdown 게이트는 여전히 검사합니다. 문서 웹사이트는 한국어 독자 안내서와 번역된 기여자 참조 페이지를 `/ko/` 트리로 투영하며, 한국어 렌더링이 없는 페이지는 영어·중국어 사이트에 남습니다.
- **언어 전환 줄.** 중국어 파일은 H1 제목 바로 다음에 항상 `[English](foo.md) | 中文`으로 역링크합니다. 사람이 작성한 영어 파일은 같은 자리에 `English | [中文](foo.zh.md)`로 응답하며, 생성된 영어 원본으로 목록에 오른 것은 이 줄을 생략해 생성기 출력과 바이트 단위로 동일하게 남습니다. 한국어 렌더링을 두는 쪽은 그 줄 끝에 `| [한국어](foo.ko.md)`를 덧붙입니다. PyPI 프로젝트 메타데이터처럼 GitHub 밖에 게시되는 README는 전환 줄이 그곳에서도 해석되도록 같은 대응 문서를 가리키는 표준 `https://github.com/deepseek-ai/deepseek-harness/blob/master/<repository-path>` URL을 써도 됩니다.
- **구조는 대응 문서를 그대로 비춥니다.** 제목 깊이와 순서, 목록 종류, 순서 목록 시작 번호, 목록 항목 수, 표의 행·열 수, 정확한 쿼리/프래그먼트 접미사를 가진 의미상 링크 대상, 그대로 옮긴 코드 블록이 쌍 양쪽에서 1:1로 일치합니다. 상대 문서 링크가 활성 이중 언어 코퍼스를 가리키면 영어 쪽은 `.md` 경로를, 중국어 쪽은 `.zh.md` 경로를 씁니다. 그 코퍼스에 대응 문서가 없는 것은 폴백이 아니라 쌍 완전성 오류입니다. 활성 코퍼스 밖 대상은 작성된 경로를 유지합니다. 전체 보존 규칙은 [translation-rules.md](translation-rules.ko.md)를 참고하세요. 기존 Markdown 게이트는 `.zh.md` 파일에도 그대로 적용됩니다(`verify-md-wrap`, `verify-md-links`).

## 게이트: verify-translation-pairing

`pnpm run verify-translation-pairing`(`doc-sync`의 일부이며, 기여자는 문서 변경 시 로컬에서, CI는 전수로 실행합니다)은 계약을 기계적으로 강제합니다:

1. 범위에 속한 모든 문서는 완전한 쌍을 가집니다. README 탐색은 파일 이름의 대소문자를 구분하지 않으므로 `missions/readme.md`도 다른 문서 루트와 함께 범위에 들어갑니다.
2. 존재하는 모든 쌍 산출물은 완전하고 일관됩니다. 세 파일이 모두 있어야 하고, 기록이 정규 형식이며 그 항목이 현재 내용에서 계산한 항목과 같아야 하며(쌍을 다시 확인하지 않고 어느 쪽이든 언어별 내용을 바꾸면 실패합니다), 중국어 쪽과 사람이 작성한 모든 영어 원본이 언어 전환 줄을 가져야 하고(생성된 영어 원본으로 목록에 오른 것은 예외), 모든 일반 상대 문서 링크가 원본 쪽의 대상 로케일을 쓰며, 구조 시그니처가 순서대로 일치해야 합니다. 제목 깊이, 그대로 옮긴 코드 블록(정보 문자열과 내용), 표의 행·열 수, 목록 종류, 순서 목록 시작 번호, 항목 수, 그리고 전환 줄을 제외한 정확한 쿼리/프래그먼트 접미사를 가진 의미상 링크 대상입니다.
3. `excluded`로 나열된 파일에는 `.zh.md`도 `.i18n.yaml`도 전혀 없습니다. `.agents/notes/archived/` 아래의 동결된 Agent Note는 이 진화하는 게이트 밖에 있으며, 전용 검증기가 대신 기존 삼중 파일의 완전성을 요구하고 봉인합니다.

소스 지향 코드 게이트는 접미사 없는 형제 파일의 파생물로서 정확한 `.zh.md` 펜스 시퀀스를 소비하며, 같은 코드를 두 번 컴파일하거나 매니페스트하지 않습니다. 시퀀스는 길이, 순서, 펜스 종류, 바이트 단위 본문이 일치해야 하며, 그렇지 않으면 두 사본을 독립적으로 검사하고 쌍 게이트가 구조 불일치를 보고합니다.

`pnpm run verify-translation-pairing --list`는 범위에 속한 모든 문서의 현재 쌍 상태(누락, 어긋남, 정상)를 출력합니다. 이 명령은 실패하지 않으며, `missing`과 `out-of-sync` 행은 일반 검사가 거부하는 위반을 가리킵니다.

`pnpm run verify-translation-pairing <pair...>`는 이름을 지정한 쌍만 검사합니다. 쌍의 세 파일 중 무엇이든(또는 확장자 없는 줄기) 이름으로 쓸 수 있으므로, 갱신 루프가 코퍼스 전체를 다시 훑지 않고 몇 초 만에 자기 쌍을 검증할 수 있습니다. 인수 없는 코퍼스 전체 형태가 `doc-sync`와 CI가 실행하는 것이며, 범위를 좁힌 통과가 PR 수준에서 이를 대신할 수는 없습니다.

이 게이트가 만들어 내는 실용 규칙은 다음과 같습니다. **PR이 쌍을 이룬 문서의 어느 쪽이든 편집하면, 같은 PR이 용어집을 참고한 한 번의 패스로 대응 문서를 직접 갱신하고 `--write <pair>`로 쌍을 다시 기록합니다.** 코드와 README에 대한 저장소의 기존 doc-sync 규칙과 정확히 같습니다. 쌍을 어긋난 채로 두는 PR은 CI에서 실패합니다.

게이트의 한계를 분명히 밝힙니다. **게이트가 통과했다는 것은 이 정확한 내용에서 쌍이 일관된다고 확인했다는 뜻이지, 그 확인이 타당했다는 뜻이 아닙니다.** 게이트는 해시와 Markdown 구조를 검사합니다. 두 쪽이 같은 것을 말하는지, 문구가 정확하고 용어가 적절하며 자연스러운지는 판단할 수 없습니다. 그것은 [translation-rules.md](translation-rules.ko.md)에 따른 계약의 리뷰어 몫입니다. 대응 문서가 엉성한 채로 다시 기록된 쌍은 게이트를 통과하지만 리뷰를 통과해서는 안 됩니다.

## 범위와 제외

**범위**: 루트의 `CONTRIBUTING.md`, `BRAND_GUIDELINES.md`, `SAFETY.md` 문서, 벤더가 아닌 모든 README, 그리고 `.agents/notes/**`, `docs/**`, `python/**` 아래의 모든 활성 문서입니다. README 매칭은 파일 이름의 대소문자를 구분하지 않으며 매니페스트를 다시 고치지 않고도 앞으로 생길 디렉터리를 포함합니다. 의존성 트리와 무시된 빌드 출력 트리, 동결된 `.agents/notes/archived/` 트리는 탐색 제외이며 진화하는 번역 원본이 아닙니다.

**범위 밖**: 번들의 상세 문서, 즉 `packages/<group>/<package>/docs/` 아래에 있고 로케일 `meta.detail`이 플러그인 페이지에 지정하는 문서입니다. 페이지는 활성 UI 언어의 파일을 보여 주므로 이 문서들에는 문서 내 언어 전환 줄도, 일관성 기록도 없습니다. [`verify-md-links`](../../scripts/verify-md-links.ts)와 [`verify-md-wrap`](../../scripts/verify-md-wrap.ts)는 여전히 두 언어를 검사하고, 리뷰가 둘을 맞춰 유지합니다.

생성된 영어 참조와 그래프는 리뷰된 중국어 대응 문서가 있을 때 쌍에 참여합니다. 생성기는 생성 데이터를 생성 영역에 넣고 각 영역을 두 페이지 모두에 쓰므로, 다시 생성할 때 중국어를 직접 고치거나 새 기록을 만들 필요가 없습니다. 영역 외부의 일반 본문 텍스트만 번역하고 기록합니다. 신선도 게이트와 쌍 게이트는 각자의 불변식을 독립적으로 강제합니다.

Cordis 하위 시스템 영역과 [config catalog](../config-catalog.ko.md)의 패키지별 영역처럼 공유되는 생성 영역은, 로케일별 쌍 문서 경로를 제외하고 모든 생성 바이트를 언어 간에 동일하게 유지합니다. 영역 안의 레이블은 번역된 단어가 아니라 코드 식별자입니다. 전체 페이지 생성기는 [persistence-catalog-text.ts](../../scripts/persistence-catalog-text.ts)처럼 소스에 포함된 다국어 본문 텍스트도 동일한 구조 데이터로부터 일치하는 Markdown 구조와 동일한 코드 블록으로 렌더링할 수 있습니다. 이 생성기는 두 페이지와 일관성 기록을 함께 재생성하며, 코드 리뷰 단계에서 본문 텍스트의 의미와 기술 용어 정합성을 검증합니다.

생성된 영어 원본은 일반 작성 원본이 가지는 언어 전환 줄을 생략합니다. 추가하면 생성기가 낡은 상태가 되기 때문입니다. 그 중국어 대응 문서는 여전히 영어 원본으로 역링크합니다. 직접 관리하는 중국어 대응 문서는 리뷰된 번역에 대해 사실이 아닐 수 있는 생성·유지 관리에 관한 자기 지시적 문장만 다시 쓸 수 있으며, 모든 기술 내용은 일반 충실성 규칙의 적용을 받습니다.

**제외**(쌍을 만들지 않으며, 게이트가 이들에 대한 `.zh.md`나 `.i18n.yaml`을 거부합니다):

- [cordis-api/inherited.md](../cordis-api/inherited.md) — 리뷰된 중국어 대응 문서 없이 생성되므로 두 웹사이트 로케일 모두 영어 원본을 투영합니다.
- `docs/AGENTS.md`, `.agents/notes/**/AGENTS.md` 및 그 `CLAUDE.md` 지침 심볼릭 링크 — 에이전트 지침이며 루트 `AGENTS.md`처럼 영어로만 유지합니다.
- `docs/i18n/terminology.md`와 [style-samples.md](style-samples.md) — 둘 다 구성상 이중 언어입니다.
- [translation-prompt.md](translation-prompt.md) — 자동화 파이프라인의 프롬프트 템플릿입니다. 본문이 기계에 그대로 소비되므로, 쌍 번역을 만들면 파이프라인 동작이 바뀝니다.
- [review-ownership/README.md](../../.github/review-ownership/README.md) — 저장소 내부 승인 정책이며 영어로만 유지합니다.
- `.agents/notes/archived/` — 동결된 역사적 삼중 파일입니다. [`verify-archived-agent-notes`](../../scripts/verify-archived-agent-notes.ts)가 완전성과 내용 봉인을 검증하며, 번역 유지 관리가 이들을 다시 쓰는 일은 없어야 합니다.

**보편 요구 사항**: 범위에 속한 현재와 미래의 모든 문서는 완전한 이중 언어 쌍으로 병합되어야 합니다. [scripts/translation-pairing.manifest.json](../../scripts/translation-pairing.manifest.json)은 명시적 제외만 담고 있으며, 파일별 롤아웃 목록도, 날짜 기준선도, README 전용 정책 분류도 없습니다.

## 역할 분담

일상적인 대응 문서는 작업 에이전트가 [terminology.md](terminology.md)를 읽어 들인 뒤 한 번의 패스로 직접 갱신합니다. 번역 스킬을 호출하거나 브리핑을 생성하거나 별도의 번역 리뷰 패스를 돌리거나 서브에이전트에 위임하지 않습니다. 확장 [dsh-translate-docs](../../.agents/skills/dsh-translate-docs/SKILL.md) 워크플로는 그 무거운 장치들을 사용자의 명시적 호출용으로 남겨 둡니다. 게이트는 쌍 완전성, 기록된 해시, 중국어 역링크와 작성 원본의 전환 줄(문서화된 생성 원본 예외 포함), 문서화된 구조 시그니처를 검사합니다. 번역 품질, 용어, 시그니처가 인코딩하지 않는 구조 요구 사항은 여전히 리뷰가 담당합니다. 프롬프트 계약은 실행 가능합니다. [scripts/translation-prompt.ts](../../scripts/translation-prompt.ts)가 커밋된 템플릿(용어 주입, 템플릿은 자체 보정 규칙을 지님)을 양방향으로 렌더링하고 세 섹션 응답을 파싱하며, `verify-translation-prompt`가 `doc-sync`에서 두 렌더 방향과 저장된 예제를 실행합니다.
